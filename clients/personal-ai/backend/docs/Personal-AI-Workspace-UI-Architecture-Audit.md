## 执行摘要

本项目是一个基于原生 JS + CSS 的单页应用，定位为「个人 AI 工作空间」。当前系统**功能可用但架构脆弱**，核心问题集中在三个方面：

1. **信息架构混乱** — 导航引用了大量不存在的模块，AI 复盘库过度膨胀，缺少统一的概念分层
2. **UI 系统碎片化** — 设计令牌已定义但未被遵守，同一种组件有 5 套实现，内联样式泛滥
3. **代码结构不可维护** — 存在 8500+ 行的巨型模块，上帝对象承担 10+ 种职责，无状态管理、无组件复用、无构建工具

**最严重的单一问题**: `obsidian-reviews` 模块（AI 复盘库）占整个前端代码量的 60% 以上，且内部完全没有结构化组织，是后续维护和扩展的最大瓶颈。

### 1.3 信息架构问题分析

#### 问题 1：导航引用大量不存在的模块

**index.html 第13行**引用了 `/modules/agent/style.css`，但 modules 目录下没有 agent 目录。

**app.js 快捷键**（第92行）定义了 Alt+1~0 切换模块，但模块列表包含：
```
['search', 'prompt', 'review', 'dashboard', 'resume', 'code', 'graph', 'learning', 'settings']
```
其中 `review`、`dashboard`、`resume`、`code`、`graph`、`learning` 六个模块**均不存在**。

**app.js loadModule**（第486-498行）的 titles 对象也包含了这些不存在模块的标题。

**影响**: 用户按 Alt+3~8 会触发 `switchModule`，但 `this.modules[module]` 为 undefined，页面空白，无任何错误提示。

#### 问题 2：AI 复盘库功能过度膨胀

AI 复盘库一个页面承担了：
- 复盘 CRUD
- 统计看板（概览、热力图、趋势图）
- 行动项管理
- 搜索 + 筛选
- 多种视图切换

这些功能中，**统计看板**和**行动项管理**实际上是独立的概念，应该与"复盘列表"平级或作为复盘库的子视图，而不是全部挤在一个页面中。

#### 问题 3：「总览 / 复盘 / 洞察 / 行动」结构判断

**判断：应该继续作为 AI 复盘库的核心结构，而不是拆成一级导航。**

理由：
1. 这四个概念本质上都是围绕「复盘」这一核心活动展开的
2. 「总览」是复盘的统计视图，「洞察」是复盘的 AI 分析结果，「行动」是复盘的产出
3. 拆成一级导航会增加认知负担，用户需要在多个页面间跳转才能完成「写复盘 → 看分析 → 跟进行动」的完整流程
4. 「少入口、多关系」原则：应该在复盘库内部用 Tab 或子导航切换这四个视图，而不是增加四个一级入口

**但当前问题是**: 这四个视图在代码中没有清晰的分层，全部混在一个 3305 行的 module.js 中。

#### 问题 4：设置页功能杂糅

设置页包含：
- Obsidian 索引配置（核心功能配置）
- 数据备份（系统运维）
- 配置导入导出（系统运维）

「索引配置」是用户日常可能需要调整的（比如添加新的索引源），而「备份」和「导入导出」是低频运维操作。三者混在一起，增加了用户找到常用设置的成本。

#### 问题 5：知识页与全局搜索功能重复

- 顶部全局搜索框：聚焦时跳转到知识页，输入同步到知识页搜索框
- 知识页内部：有自己的搜索框

这两个搜索框**功能完全重复**，通过 DOM 事件同步（app.js 第199-237行），实现方式 hacky 且容易出 bug。

#### 问题 6：缺少「首页 / 总览」概念

用户打开工作台后，默认进入「知识」页。但工作台的定位是「个人 AI 工作空间」，应该有一个总览页，展示：
- 最近访问的知识
- 最近的复盘
- 待办行动项
- 索引状态
- 快速入口

当前缺少这个「聚合层」，用户打开后直接进入搜索页，缺少「我现在在哪里、这里有什么」的定位感。

### 1.4 导航认知负担评估

| 评估维度 | 当前状态 | 评分 |
|----------|----------|------|
| 一级导航数量 | 5个可用 + 2个禁用 = 7个 | ⚠️ 偏多 |
| 导航概念一致性 | 知识/提示词/复盘是内容，网站后台是运维，设置是系统 | ❌ 不一致 |
| 禁用项比例 | 2/7 = 29% | ❌ 过高 |
| 功能重复 | 全局搜索 vs 知识页搜索 | ❌ 重复 |
| 缺失概念 | 无首页/总览，无个人中心 | ⚠️ 缺失 |

**结论**: 当前导航存在中等偏高的认知负担。主要问题不是导航项太多，而是**概念不统一**（内容类和运维类混在一起）和**功能重复**（两个搜索框）。

## 2. 当前 UI 系统审计

### 2.1 设计令牌现状

**已定义**: main.css :root 中定义了约 120 个设计令牌，覆盖：
- 颜色（canvas, surface-1/2/3, accent, sem-*, text-*）
- 背景层级（bg-app/surface/subtle/muted/hover）
- 边框（border-subtle/default/strong, separator）
- 玻璃拟态（glass-bg/strong/border/blur/shadow）
- 新拟态阴影（nm-xs/sm/md/lg, nm-inset-*）
- 浮动阴影（float-xs/sm/md/lg/hover）
- 字体（font-sans/mono, text-xs~display, leading-*, weight-*）
- 尺寸（sidebar-width, topbar-height, content-max）
- 间距（space-px~space-10，4px网格）
- 圆角（radius-xs~3xl, pill）
- 过渡（transition-fast/base/slow, ease-out）

**令牌使用率**: 
- 全局样式（main.css）var() 引用约 425 次，使用率高
- 模块样式中大量硬编码（刚完成 P0 统一，仍有残留）
- 兼容别名约 40+ 个（apple-*, nm-*, system-*, shadow-* 等），部分使用了错误颜色

**深色模式**: `[data-theme="dark"]` 完整覆盖了基础令牌，但模块中的硬编码颜色在深色模式下可能显示异常。

### 2.3 组件审计

#### Card（卡片）
- **实现数量**: 每个模块自己实现卡片样式，至少 5 套
- **不统一问题**:
  - 圆角：8px / 10px / 12px / 14px / 16px / 20px 多种
  - 内边距：12px / 14px / 16px / 20px / 24px 多种
  - 阴影：无阴影 / float-xs / float-sm / 硬编码阴影 多种
  - 背景：surface-1 / 各种白色半透明（已统一）
  - 边框：无边框 / border-subtle / border-default 多种
- **过度卡片化**: 设置页中统计数据用了 3 个卡片包裹，复盘列表中每个复盘是卡片，行动项也是卡片，页面视觉层次被卡片切割

#### Button（按钮）
- **实现数量**: 全局定义了 .btn 基础类 + .btn-primary/.btn-outline/.btn-ghost/.btn-danger 变体 + .btn-sm 尺寸
- **不统一问题**:
  - 模块中大量使用自定义按钮（内联样式或模块类）
  - 按钮高度不统一（28px / 32px / 36px / 40px / 44px）
  - 按钮圆角不统一（6px / 8px / 10px / 12px）
  - 危险按钮颜色不统一（#e74c3c / #ef4444 / var(--sem-red)）
  - Personal AI 面板中的按钮完全自定义

#### Input（输入框）
- **实现数量**: 全局 .form-input + 模块自定义
- **不统一问题**:
  - 高度不统一（32px / 36px / 40px）
  - 圆角不统一（6px / 8px / 10px）
  - 焦点样式不统一（有的有 focus ring，有的没有）
  - 占位符颜色不统一

#### Modal（模态框）
- **实现数量**: 至少 3 套
  1. 全局通用模态框（#modalOverlay，在 index.html 中）
  2. 知识模块的笔记详情模态（.note-detail-modal，动态创建）
  3. 提示词库的 Prompt 编辑模态（.prompt-modal，动态创建）
- **问题**:
  - 三套模态框的样式、动画、关闭逻辑都不相同
  - 全局模态框的关闭按钮需要「克隆替换」来确保事件绑定（api.js 第148-154行），这是明显的 workaround
  - ESC 关闭逻辑在多处重复实现（app.js 第99-111行 + api.js 第164-175行）

#### Drawer（侧边详情面板）
- **实现**: 知识模块和复盘模块都有侧边详情面板，但实现方式不同
- **问题**: 没有统一的 Drawer 组件，每个模块自己实现

#### Tabs（标签页）
- **实现数量**: 每个模块自己实现
- **不统一问题**: 激活样式、下划线、动画都不统一

#### Badge（徽章/标签）
- **实现数量**: 每个模块自己实现标签样式
- **不统一问题**: 颜色体系不统一（知识模块的类型标签、复盘模块的来源标签、Prompt 模块的分类标签各有各的颜色）
- **颜色数量**: 仅复盘模块就有 7+ 种来源标签颜色

#### Toast（通知）
- **实现**: 全局统一（UI.toast，在 api.js 中）
- **状态**: ✅ 统一，4 种类型（success/error/warning/info）
- **问题**: 使用 emoji 图标（✅❌⚠️ℹ️），在不同平台渲染不一致

#### Dropdown（下拉菜单）
- **实现**: 几乎没有统一的 Dropdown 组件
- **问题**: 筛选、排序等功能用模态框或内联展开实现，交互不一致

#### Table（表格）
- **实现**: 复盘模块的 Markdown 表格 + 备份列表
- **问题**: 没有统一的表格组件，样式简陋

#### Empty State（空状态）
- **实现**: 各模块自己实现
- **问题**: 有的有图标+文字，有的只有一行文字，有的完全空白

#### Loading State（加载状态）
- **实现**: 全局 loading overlay（UI.showLoading）+ 模块内联 loading
- **问题**: 全局 loading 是全屏遮罩，阻塞用户操作；模块内联 loading 样式不统一

### 2.4 视觉语言问题

#### 过度卡片化
- 设置页：3 个统计卡片 + 1 个配置卡片 + 1 个备份卡片 + 1 个导入导出卡片 = 6 个卡片堆叠
- 复盘列表：每个复盘是卡片，卡片内还有子卡片（统计、行动项）
- 知识搜索结果：每条结果是卡片
- **问题**: 卡片过多导致页面被切割成碎片，视觉层次扁平，缺少「页面感」

#### 过度留白
- 内容区左右留白过大
- 卡片内边距普遍偏大（16-24px）
- 模块之间间距不统一
- **问题**: 信息密度过低，一屏能看到的内容有限

#### 过度使用边框
- 卡片有边框
- 卡片内的分隔区域有边框
- 列表项有边框
- 输入框有边框
- **问题**: 边框过多导致视觉噪音，应该用间距和背景色区分区域，而不是边框

#### 视觉层级混乱
- 页面标题、模块标题、卡片标题、内容标题的字号层级不清晰
- 重要操作和次要操作的视觉权重区分不够
- 状态色（成功/警告/危险）使用不一致

#### 不必要的装饰
- 侧边栏导航项使用 emoji 图标（📚✍️📝🌐⚙️）
- Toast 使用 emoji 图标
- 设置页使用 emoji 作为分区图标
- **问题**: emoji 在不同平台渲染不一致，且与「柔和科技感」定位不符

#### 玻璃拟态使用
- 定义了完整的玻璃拟态令牌（glass-bg/strong/border/blur/shadow）
- 但实际使用中，卡片背景已统一为 surface-1（不透明）
- **问题**: 玻璃拟态令牌定义了但未充分使用，与「不要明显的玻璃拟态」要求一致，但令牌冗余

### 3.2 结构问题分析

#### 问题 1：缺少标准前端工程结构

**缺失的目录/概念**:
- ❌ `components/` — 无共享组件目录
- ❌ `hooks/` — 无自定义 Hooks
- ❌ `utils/` — 无工具函数目录（UI 工具混在 api.js 中）
- ❌ `services/` — 无服务层（API 调用混在模块中）
- ❌ `store/` 或 `state/` — 无状态管理
- ❌ `types/` — 无 TypeScript 类型定义
- ❌ `assets/` — 无静态资源目录（虽然 public 下有 assets，但为空）
- ❌ 构建工具（Vite/Webpack/esbuild）
- ❌ 包管理配置（package.json 在根目录，但前端无依赖）

**前端技术栈**: 原生 JS + 原生 CSS，无框架、无构建、无模块化（全部通过 `<script>` 标签加载全局变量）

#### 问题 2：巨型模块 — obsidian-reviews

| 指标 | 数值 | 占比 |
|------|------|------|
| module.js 行数 | 3305 行 | 前端 JS 总量的 65% |
| style.css 行数 | 5264 行 | 前端 CSS 总量的 55% |
| 选择器数量 | 721 个 | — |
| 函数/方法匹配数 | 1 个 | ⚠️ 说明几乎没有结构化函数定义 |

**内部结构问题**:
- 3305 行代码只匹配到 1 个函数定义（正则匹配），说明：
  - 大量使用全局函数（`function foo()` 可能被正则漏匹配，但更可能是大量内联回调）
  - 大量使用事件监听器内联回调
  - 大量使用 IIFE 或直接执行的代码块
  - 代码按「功能段落」组织，而不是按函数/模块组织
- 5264 行 CSS，721 个选择器，说明：
  - 每个功能区块都有自己的样式类
  - 类名命名不统一（有的用 `.obs-` 前缀，有的没有）
  - 大量重复的样式模式（卡片、按钮、标签各写一遍）

**可维护性评估**: ❌ 极低。任何修改都需要在 3000+ 行代码中定位，且无法确定修改是否会影响其他功能。

#### 问题 3：上帝对象 — App

`App` 对象（app.js，804行）承担了以下职责：

| 职责 | 行数/方法 | 是否应该独立 |
|------|-----------|-------------|
| 模块路由与切换 | switchModule, loadModule, registerModule | ✅ 应该独立为 Router |
| 主题管理 | initTheme, bindTheme, updateThemeToggleIcon | ✅ 应该独立为 ThemeManager |
| 快捷键绑定 | bindShortcuts | ✅ 应该独立为 ShortcutManager |
| 导航绑定 | bindNav, save/restoreNavGroupState | ✅ 应该独立为 NavManager |
| 侧边栏折叠 | bindSidebarCollapse, toggleSidebar, restoreSidebarCollapse | ✅ 应该独立 |
| 侧边栏拖拽排序 | bindSidebarEdit, enter/exitEditMode, _onDrag*, save/restore/resetNavOrder | ✅ 应该独立为 NavEditor（~150行） |
| 顶部搜索同步 | bindTopbarSearch, bindTopSearchInput | ✅ 应该独立 |
| 设置页面渲染 | renderSettings（~100行内联HTML + 事件绑定） | ✅ 应该独立为 Settings 模块 |
| 备份管理 | createBackup, loadBackupList, restoreBackup, deleteBackup | ✅ 应该独立为 BackupService |
| 配置导入导出 | exportConfig, importConfig | ✅ 应该独立 |
| 索引状态更新 | updateIndexStatus（setInterval 5秒轮询） | ✅ 应该独立 |
| 额外路径管理 | renderExtraPathsList, _removeExtraPath | ✅ 应该独立 |
| Vault 统计 | loadVaultStats | ✅ 应该独立 |
| Electron 集成 | initElectron | ✅ 应该独立 |

**总计**: 15+ 种职责，804 行代码，是典型的上帝对象。

**问题**: 任何一个职责的修改都可能影响其他职责，且无法单独测试。

#### 问题 4：UI 工具函数与 API 封装混在一起

`api.js`（184行）包含两个完全不相关的全局对象：
- `API` — 所有后端接口的封装（~80行）
- `UI` — UI 工具函数（loading, toast, modal, escapeHtml, formatDate）（~100行）

**问题**: API 层和 UI 层应该分离，当前混在一起违反了单一职责原则。

#### 问题 5：模块注册机制脆弱

**当前机制**:
```javascript
// 模块中
App.registerModule('search', { render(target) { ... }, doSearch() { ... }, ... });

// App 中
loadModule(module) {
  if (this.modules[module] && typeof this.modules[module].render === 'function') {
    this.modules[module].render(target);
  }
}
```

**问题**:
1. 模块接口没有约定 — 有的模块有 `render`，有的有 `focusSearch`，有的有 `doSearch`，App 中用 `typeof this.modules.search.focusSearch === 'function'` 来判断，脆弱
2. 模块状态丢失 — 切换模块时直接 `innerHTML = ''`，模块内的所有状态（搜索关键词、筛选条件、滚动位置）全部丢失
3. 模块间通信困难 — 只能通过全局事件或 DOM 操作通信
4. 无生命周期 — 没有 `onMount`/`onUnmount`/`onUpdate` 等生命周期钩子

#### 问题 6：UI 与业务逻辑严重耦合

**表现**:
- 模块直接操作 DOM（`document.getElementById`、`innerHTML`、`addEventListener`）
- 模块直接调用 API（`API.search()`、`API.getReviews()`）
- 数据转换在事件回调中完成
- 没有数据层抽象

**示例**（知识模块搜索流程）:
```
用户输入 → input 事件回调 → 直接调用 API.search() → 
在 .then() 中直接操作 DOM 渲染结果 → 每个结果项手动拼接 HTML 字符串
```

**问题**: 无法单独测试业务逻辑，无法复用数据获取逻辑，UI 变更需要重写业务逻辑。

#### 问题 7：内联样式泛滥

**设置页**（app.js renderSettings）:
- 完全用内联样式渲染（`style="max-width:650px;"`、`style="margin-bottom:16px;"` 等）
- 约 50 处内联样式
- 使用了不存在的 CSS 变量（`var(--bg-secondary)`、`var(--bg-tertiary)`、`var(--border-color)`）

**其他模块**:
- 动态创建的元素大量使用内联样式
- 一次性样式直接写在 HTML 字符串中

**问题**: 内联样式无法被设计令牌统一管理，无法被主题切换覆盖，无法被 CSS 优化工具处理。

#### 问题 8：临时 Workaround

1. **Modal 关闭按钮克隆替换**（api.js 第148-154行）:
   ```javascript
   const oldCloseBtn = document.getElementById('modalClose');
   const newCloseBtn = oldCloseBtn.cloneNode(true);
   oldCloseBtn.parentNode.replaceChild(newCloseBtn, oldCloseBtn);
   newCloseBtn.addEventListener('click', () => UI.hideModal());
   ```
   原因：事件监听器被其他地方移除或阻止，需要通过克隆重新绑定。这是明显的代码异味。

2. **Modal 事件绑定标记**（api.js 第156-163行）:
   ```javascript
   if (!overlay.__modalOverlayClickBound) { ... }
   ```
   用 DOM 元素的自定义属性标记事件是否已绑定，说明事件绑定逻辑混乱。

3. **顶部搜索与模块搜索同步**（app.js 第199-237行）:
   - 顶部搜索框聚焦时跳转模块
   - 输入时通过 `setTimeout 50ms` 同步到模块搜索框
   - 通过 `dispatchEvent(new Event('input'))` 触发模块搜索
   - 这是典型的「两个状态源需要同步」问题，应该通过状态管理解决

4. **ESC 关闭重复实现**:
   - app.js 第99-111行：处理通用模态 + 笔记详情模态 + Prompt 模态
   - api.js 第164-175行：处理通用模态
   - 两处都处理通用模态，逻辑重复

#### 问题 9：死代码与冗余

1. **引用不存在的模块**:
   - index.html 引用 `/modules/agent/style.css`（不存在）

2. **兼容别名**:
   - main.css 中有 40+ 个兼容别名（apple-*, nm-*, system-*, shadow-* 等）

### 4.2 数据流问题分析

#### 问题 1：无数据缓存

**当前行为**:
- 每次切换模块 → `innerHTML = ''` → 重新调用 API → 重新渲染
- 同一模块内，每次筛选/搜索都重新调用 API
- 没有任何客户端缓存（Memory Cache / LocalStorage Cache / IndexedDB）

**影响**:
- 模块切换慢（需要等待 API 返回）
- 重复请求相同数据（比如复盘列表，切换出去再切回来又请求一次）
- 服务器压力大
- 用户体验差（每次切换都看到 loading）

#### 问题 2：无状态管理

**当前状态存储方式**:
1. **DOM 中**: 搜索框的值、筛选条件的选中状态、列表的滚动位置
2. **模块闭包中**: `let currentPage = 1`、`let reviews = []` 等模块级变量
3. **LocalStorage 中**: 主题、侧边栏宽度、导航顺序、导航折叠状态
4. **全局变量中**: `App.currentModule`、`App._editMode` 等

**问题**:
- 状态分散在 4 个地方，无法统一管理
- 模块切换时，DOM 状态和闭包状态全部丢失
- 无法做时间旅行调试
- 无法做状态持久化（除了手动写 LocalStorage）

#### 问题 3：组件直接访问 API

**表现**: 每个模块的事件回调中直接调用 `API.xxx()`，没有服务层抽象。

**示例**:
```javascript
// 知识模块
searchInput.addEventListener('input', () => {
  API.search(searchInput.value).then(results => {
    // 直接渲染
  });
});

// 复盘模块
filterSelect.addEventListener('change', () => {
  API.getReviews().then(reviews => {
    // 直接渲染
  });
});
```

**问题**:
- API 调用逻辑分散在各个模块中，无法统一处理错误、加载状态、缓存
- 同一个 API 可能在多个模块中被调用，参数和处理逻辑不一致
- 更换 API 实现需要修改所有模块

#### 问题 4：数据逻辑重复

**重复的数据处理逻辑**:
1. **日期格式化**: `UI.formatDate` 和 `UI.formatDateTime` 定义了，但模块中大量使用 `new Date().toLocaleDateString('zh-CN')` 直接格式化
2. **HTML 转义**: `UI.escapeHtml` 定义了，但部分模块直接拼接用户输入（XSS 风险）
3. **列表渲染**: 每个模块都有自己的「数据数组 → HTML 字符串 → innerHTML」逻辑
4. **空状态渲染**: 每个模块都有自己的空状态判断和渲染
5. **错误处理**: 每个模块的 `.catch()` 逻辑不同，有的 toast，有的 console.error，有的静默

#### 问题 5：顶部搜索与模块搜索的双数据源

**当前流程**:
```
用户在顶部搜索框输入
  → input 事件
  → setTimeout 50ms
  → 找到模块搜索框（getElementById）
  → 同步 value
  → dispatchEvent(new Event('input'))
  → 模块搜索框的 input 事件触发
  → 调用 API.search()
  → 渲染结果
```

**问题**:
- 两个搜索框是两个独立的状态源，需要手动同步
- setTimeout 50ms 是 hacky 的延迟，可能不够或多余
- dispatchEvent 触发的事件可能与用户真实输入行为不一致
- 如果模块搜索框不存在（模块未加载），同步失败
- 反向同步（模块搜索框输入 → 顶部搜索框）不存在，两个搜索框的值可能不一致

#### 问题 6：Personal AI 数据流独立

**Personal AI 面板**:
- 有自己的 API 路由（`/api/personal-ai/*`）
- 有自己的状态管理（对话历史存在模块闭包中）
- 有自己的 UI 渲染逻辑
- 与其他模块几乎没有数据交互

**问题**: Personal AI 应该是工作台的「智能助手」，能够感知用户当前在看什么、做什么，但当前完全独立，无法获取其他模块的上下文。

## 5. UI 重构建议

### 5.1 重构原则

1. **少入口、多关系** — 减少一级导航数量，通过页面内的子导航、筛选、关联展示功能间的关系
2. **功能聚合** — 相关功能聚合在一个页面，用 Tab 或分区切换，而不是多个平级页面
3. **个人工作空间定位** — 不是后台管理系统，不需要「列表页 → 详情页」的传统 CRUD 结构
4. **低认知负担** — 用户打开页面后，3 秒内知道「我在哪里、这里有什么、我可以做什么」
5. **视觉克制** — 减少卡片、边框、装饰，用间距、字号、颜色层级区分内容

### 5.2 推荐的整体 Layout

```
┌──────────────────────────────────────────────────────────────┐
│  [Logo/名称]  [页面标题 + 面包屑]          [搜索] [AI] [设置] │  Header (48px)
├────────┬─────────────────────────────────────────────────────┤
│        │                                                     │
│  导航   │                  内容区                              │
│  (64px │              (最大宽度 960px，居中)                   │
│  图标   │                                                     │
```

**Layout 变更要点**:
1. **Header 增加页面标题和面包屑** — 用户知道当前在哪里

- ❌ 英语学习 — 未实现，移除（未来实现后作为独立模块）
- ❌ 全局搜索框 — 移到 Header 右侧，不再是独立区域

**一级导航数量**: 4 个内容导航 + 2 个系统导航 = 6 个（比当前 7 个少，且概念更统一）

### 5.4 推荐的二级导航（页面内 Tab）

#### 总览页（无 Tab，单页聚合）
- 欢迎区（问候语 + 日期 + 索引状态）
- 最近访问（知识 + 复盘，混合列表）
- 待办行动项（来自复盘的行动项）
- 快速入口（新建复盘、搜索知识、管理 Prompt）
- 信息流（未来信息雷达实现后放在这里）

#### 知识页（无 Tab，搜索即首页）
- 搜索框（页面顶部，大而突出）
- 搜索模式切换（关键词/语义/混合，作为搜索框的附属控件）
- 搜索历史（搜索框下方，无输入时显示）
- 搜索结果（输入后显示）
- 知识详情（点击结果后右侧 Drawer 打开）

#### 复盘页（4 个 Tab）
| Tab | 内容 | 定位 |
|-----|------|------|
| 复盘 | 复盘列表 + 搜索 + 筛选 | 核心功能 |
| 总览 | 统计概览 + 热力图 + 趋势 | 数据洞察 |
| 行动 | 行动项列表 + 新建 + 完成 | 跟进执行 |
| 洞察 | AI 生成的复盘洞察、模式识别 | AI 增值 |

**为什么用 Tab 而不是一级导航**: 这四个概念都围绕「复盘」展开，用户在「写复盘 → 看统计 → 跟进行动 → 获得洞察」的流程中需要频繁切换，Tab 切换比页面跳转成本低。

#### 提示词页（无 Tab，列表即首页）
- 分类筛选（左侧或顶部）
- Prompt 列表（卡片或列表）
- Prompt 详情/编辑（点击后右侧 Drawer 或 Modal）
- AI 生成按钮（顶部主要操作）

### 5.5 页面层级与关系

```
总览（Home）
├── 最近知识 → 知识页（带搜索关键词）
├── 最近复盘 → 复盘页（复盘 Tab，带筛选）
├── 待办行动 → 复盘页（行动 Tab）
└── 快速入口 → 各页面

知识页
├── 搜索结果 → 知识详情（Drawer）
├── 知识详情 → 相关知识（关联推荐）
└── 知识详情 → 来源笔记（Obsidian 链接）

复盘页
├── 复盘 Tab → 复盘详情（Drawer 或 Modal）
│   ├── 复盘内容
│   ├── AI 分析
│   ├── 坑点
│   └── 关联行动项 → 行动 Tab
├── 总览 Tab → 统计图表
│   └── 点击数据点 → 复盘 Tab（带时间筛选）
├── 行动 Tab → 行动项详情
│   └── 关联复盘 → 复盘详情
└── 洞察 Tab → AI 洞察列表
    └── 关联复盘 → 复盘详情

提示词页
├── Prompt 列表 → Prompt 详情（Drawer）
│   ├── 编辑
│   ├── AI 迭代
│   └── 使用历史
└── AI 生成 → 新 Prompt（Modal）
```

### 5.6 应该合并的功能

| 功能 A | 功能 B | 合并方式 | 理由 |
|--------|--------|----------|------|
| 顶部全局搜索 | 知识页搜索 | 合并为一个搜索框，放在 Header | 功能完全重复，双数据源同步 hacky |
| 设置页-索引配置 | 设置页-备份 | 索引配置保留在设置，备份移到「系统运维」分区 | 常用配置 vs 低频运维，不应混在一起 |
| 复盘列表-统计卡片 | 复盘-总览 Tab | 统计卡片移到总览 Tab，复盘列表只保留列表 | 统计和列表是不同维度，挤在一起增加认知负担 |
| 各模块的空状态 | 统一空状态组件 | 所有模块使用统一的 EmptyState 组件 | 样式不统一，体验不一致 |
| 各模块的加载状态 | 统一加载组件 | 所有模块使用统一的 Loading 组件 | 全屏 loading 阻塞操作，应该用局部 loading |

### 5.7 应该降级为筛选/属性/模块的功能

| 当前定位 | 建议定位 | 理由 |
|----------|----------|------|
| 搜索模式（关键词/语义/混合） | 搜索框的附属筛选控件 | 不是独立功能，是搜索的参数 |
| 复盘分类/标签 | 复盘列表的筛选条件 | 不是独立页面，是列表的筛选维度 |
| Prompt 分类 | Prompt 列表的筛选条件 | 同上 |
| 行动项状态（待办/完成） | 行动列表的筛选条件 | 同上 |
| 索引状态 | Header 或总览页的状态指示器 | 不是独立功能，是系统状态 |
| 备份/导入导出 | 设置页的「系统运维」分区 | 低频运维操作，不应与常用配置平级 |

### 5.8 应该删除的功能/代码

| 项目 | 理由 |
|------|------|
| index.html 中引用的 /modules/agent/style.css | 模块不存在，404 |
| app.js 中 6 个不存在模块的快捷键和标题 | 按了没反应，用户困惑 |
| main.css 中 40+ 个兼容别名 | 大部分不再使用，增加维护成本 |
| main.css.bak / main.css.v7.bak | 备份文件，不应该在源码目录 |
| backend/ 下 8 个日志文件 | 运行时产物，不应该在源码目录 |
| 侧边栏拖拽排序功能 | 用户几乎不会调整导航顺序，增加了 150+ 行代码和复杂度 |
| 侧边栏可拖拽调整宽度 | 固定宽度即可，resizer 增加了复杂度和视觉噪音 |
| 设置页中的 3 个统计卡片 | 索引统计应该在总览页，设置页不需要 |

## 6. 最终重构方案

### Phase 0：设计系统

**目标**: 建立统一的、可执行的设计令牌系统和组件库基础

**要改什么**:
1. 清理 main.css 中的兼容别名，保留核心令牌
2. 补充缺失的令牌（z-index、字间距、边框宽度、图标尺寸、组件尺寸）
3. 建立组件令牌层（button、input、card、badge、modal、drawer、tabs、dropdown、table、empty、loading、toast）
4. 创建 `core/components/` 目录，实现基础组件的 CSS 类
5. 建立设计令牌文档（HTML 预览页）

**为什么改**:
- 当前设计令牌定义了但未被遵守，组件有 5 套实现
- 没有组件库，每个模块重复造轮子
- 后续所有页面重构都依赖统一的设计系统

**涉及文件**:
- 修改: `core/main.css`
- 新增: `core/components/` 目录（button.css, input.css, card.css, badge.css, modal.css, drawer.css, tabs.css, dropdown.css, table.css, empty.css, loading.css, toast.css）
- 新增: `core/tokens/` 目录（foundation.css, semantic.css, components.css）
- 新增: 设计令牌预览页

**风险**: 低。只新增样式，不修改现有模块。

**是否可以独立完成**: ✅ 是。

**验收标准**:
- 设计令牌覆盖所有基础维度（颜色、字体、间距、圆角、阴影、动效、z-index）
- 基础组件 CSS 类定义完整，有统一的命名规范
- 设计令牌预览页可访问，展示所有令牌和组件
- 现有模块样式不受影响（向后兼容）

**目标**: 重构整体布局结构，建立新的 Header、Sidebar、Content 区域

**要改什么**:
1. 重构 index.html 的布局结构
   - Header：Logo + 页面标题 + 搜索框 + AI 入口 + 设置入口

**为什么改**:

**是否可以独立完成**: ✅ 是。在 Phase 0 完成后，Layout 可以独立重构，模块内容暂时保持不变。

**验收标准**:
- Header 包含 Logo、页面标题、搜索框、AI 入口、设置入口
- Sidebar 为图标模式，hover 显示 tooltip，点击切换模块

### Phase 2：核心组件

**目标**: 实现统一的组件库，替换各模块中的重复组件实现

**要改什么**:
1. 实现 Button 组件（primary/secondary/ghost/danger + sm/md/lg）

**风险**: 低。只新增组件，不强制修改现有模块。

**是否可以独立完成**: ✅ 是。组件库可以独立开发和测试。

**验收标准**:
- 12 种核心组件全部实现，有统一的 API 和命名规范
- 每种组件有完整的状态（default/hover/active/focus/disabled）
- Modal 组件统一处理 ESC 关闭、点击遮罩关闭、动画，无需克隆按钮
- Drawer 组件支持右侧滑出，有遮罩、动画、ESC 关闭
- 组件文档页可访问，展示所有组件和状态
- 组件使用设计令牌，不硬编码颜色/尺寸
- 组件可访问性：键盘操作、焦点管理、ARIA 标签

### Phase 5：数据层整理

**目标**: 建立统一的数据层，实现状态管理、数据缓存、服务层抽象

**要改什么**:
1. 实现服务层（Services）
   - KnowledgeService（知识搜索、获取、列表）
   - ReviewService（复盘 CRUD、统计、行动项）
   - PromptService（Prompt CRUD、生成、迭代）
   - StatsService（统计数据）
   - SettingsService（配置、备份、索引）
   - WebsiteService（网站后台数据）
2. 实现状态管理（Store）
   - 轻量级状态管理（不引入 Redux/Vuex，用发布订阅模式）
   - 全局状态：当前模块、当前页面标题、搜索关键词、加载状态
   - 模块状态：各模块的筛选条件、列表数据、详情数据
   - 状态持久化：主题、侧边栏状态、用户偏好
3. 实现数据缓存（Cache）
   - Memory Cache（会话级缓存，带 TTL）
   - API 响应缓存（相同请求短时间内不重复请求）
   - 模块切换时保留数据（不重新请求）
4. 实现模块生命周期
   - onMount（模块加载时）
   - onUnmount（模块卸载时）
   - onUpdate（状态更新时）
   - 模块切换时保留状态（搜索关键词、筛选、滚动位置）
5. 整合 API 层
   - 所有 API 调用通过 Service 层，模块不直接调用 API
   - 统一错误处理、加载状态、重试逻辑
6. Personal AI 上下文感知
   - Personal AI 可以获取当前模块、当前查看的知识/复盘、搜索关键词
   - 为未来「AI 感知用户上下文」打基础

**为什么改**:
- 当前无状态管理，模块切换状态全部丢失
- 无数据缓存，重复请求严重
- 组件直接访问 API，UI 与业务逻辑耦合
- 数据处理逻辑重复（日期格式化、HTML 转义、列表渲染）
- Personal AI 无法感知用户上下文

**涉及文件**:
- 新增: `core/services/` 目录（各 Service）
- 新增: `core/store/` 目录（状态管理）
- 新增: `core/cache/` 目录（数据缓存）
- 修改: `core/api.js`（只保留底层 fetch 封装）
- 修改: 各模块（使用 Service + Store，不直接操作 DOM/API）
- 修改: `core/app.js`（路由与生命周期整合）

**风险**: 高。数据层变更是架构级变更，需要确保所有模块正常工作。

**是否可以独立完成**: ⚠️ 部分。Service/Store/Cache 可以独立开发，但模块迁移需要逐个进行。

**验收标准**:
- 所有 API 调用通过 Service 层，模块中无直接 `API.xxx()` 调用
- 模块切换时保留状态（搜索关键词、筛选条件、滚动位置）
- 相同 API 请求在 TTL 内不重复发送（Network 面板可验证）
- 模块有清晰的生命周期（onMount/onUnmount/onUpdate）
- 状态变更触发 UI 更新，无需手动操作 DOM
- Personal AI 可以获取当前模块、当前查看内容、搜索关键词
- 错误处理统一：网络错误、API 错误、超时都有统一处理
- 加载状态统一：全局加载和局部加载区分使用
